## 本轮修复

| 改动 | 作用 |
|---|---|
| 公开概览由实际文件变更生成 | 被复核否决的候选不再通过概览变成公开“确认缺陷” |
| 装饰器定义的有界静态上下文 | 补充定义与调用契约线索；不执行代码，不冒充完整调用图 |
| 固定源码引用校验 | 确认/否决必须给出能核对的版本、路径、行号和原文；未知前提不能被忽略 |
| 跨批次候选保留 | 可保留同 PR 其他选中文件的问题，不自动认定另一个批次已审完 |
| 唯一引用与 diff 定位 | 不再沿用模型猜测的行号；无法唯一定位时只进总结 |
| 工具参数与最终格式分别纠错 | 仍共享原有请求上限，不新增隐形轮次或延长 deadline |
| 失败证据与局部结论保留 | 未完整批次保留已独立核对的结论、未知项和待复核候选，不伪装完整 |
| Webhook 与发布保护 | 签名、白名单、草稿过滤、重复投递、并发发评、旧 head 拦截有针对性测试 |
| 服务生命周期 | 停机停止领取新任务并等待在途任务；就绪状态不冒充质量放行 |
| 默认离线回归 | 测试阻断外部网络，真实模型测试独立执行；补充状态复制恢复测试 |

引用真实源码只是语义正确的必要条件，不足以自动证明因果关系和触发可达性。进程内去重不是分布式 exactly-once。

## 两个复杂样例为何仍不放行

### #269：候选发现与格式／证据完成是两回事

首轮模型确认了真实的三参函数被两参调用：`_common.py:53` 定义与 `patch_reference_moe.py:75` 调用不匹配。

复测中，模型也在第二批最后一次生成提交中列出了这个缺陷，但缺少必填 `coverageComplete`，且该阶段轮次已耗尽。因此候选保留为待复核，没有被提升为确认问题。第一批的证据不完整也阻止了原路径接受该批结果。

最新宿主对冻结的 11 次真实响应做了**离线重处理**：保留 2 个未知项、1 个否决项，整次仍未完整；没有补造或自动确认第二批缺陷。另对首轮真实确认结果单独验证，能准确定位到第 75 行。这两个检查不能拼成一次成功的新模型实测，也没有新的模型耗时。

最初离线重处理的断言错误地预期“已知问题已经复核”，首次失败保留；修正断言后分别检查待复核状态和首轮引用定位。它不是修正模型答案。

其他 GELU、图捕获等判断涉及确切依赖契约。未找到所需公开标签、PyPI 访问超时均不证明该版本不存在；没有 vLLM 0.28.1 精确源码时保留未知。

### #315：不能把设计差异直接判成新增 bug

复测已走完格式纠错并进入复核。模型提出“覆盖检查不使 GitHub run 失败”的候选，但退出码依赖私有 `CInotificate`，且调用方明确传入 `record_dashhub: true`，原有发布与测试互不阻断。该候选保留为未知，没有发布为确认 bug。

这证明部分安全约束生效，但外部契约仍不足，耗时 416.736 秒，不满足“完整且快”的质量目标。

## 上线前剩余门槛与顺序

1. **先补可靠性，而非放宽证据标准：**改善最终 schema 遵从、在现有预算内合理安排收尾、避免重复宽搜索；以固定失败响应做回归，再用未调优样本检查召回和误报。
2. **业务质量放行：**维护者裁定问题、未知项和可接受时延；单个合成样例通过不能替代独立业务样本验收。当前复杂样例仍不通过，不建议作为自动权威审查上线。
3. **运维门槛：**操作者提供私有正式配置、轮换聊天中暴露的密钥、明确仓库范围和加密连接，验证真实外部 Webhook → 队列 → 模型 → 评论、持久化恢复与回滚。
